# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-cause | The candidate plan's stated cause, read against every step, control run, and `--debug`/timing output in the repro evidence block (and any maintainer confirmation in the thread highlights) | Pass if the plan names a specific cause AND no repro step or control contradicts it. Fail if the plan names no cause, or if any step/control shows the bug still happening with the blamed component excluded, or shows the blamed component working correctly in the same build (the control "rules it out"). A cause that matches what the thread suggests but that the repro evidence contradicts still fails. | required |
| bounded-scope | Every change listed in the candidate plan (change/approach section, files, "while I'm here" items), read against the behavior the issue and repro evidence describe | Pass if every planned change is needed to fix the reproduced behavior. Fail if the plan also commits to any work the issue did not ask for: a refactor, rewrite, migration, dependency upgrade, new option/setting/UI, new framework, CI or test-harness change, or "unify across other constructs", even when the core fix inside it is correct. Work the plan explicitly defers or marks out of scope does not count against it; an honest scope-down is a pass. | required |
| executable | The candidate plan's named files, functions, or code sites, and its chosen approach | Pass if a stranger could start the edit today: the plan names at least one concrete code location (file, function, branch, or callback) AND commits to one approach. Fail if the location is "somewhere", the layer or approach is left open ("X or Y, whichever is easier", "not sure which"), or the first step is "investigate / profile / poke around" with no decided change. Short plans can pass. | required |
| decisive-test | The candidate plan's test plan, read against the repro evidence step that showed the bug | Pass if the test names an observable result that would differ between broken and fixed: a specific output, exit code, value, rendered state, or the repro step re-run with its expected post-fix result. Fail if the only test is "run the full test suite", "should feel fast", "nothing else should break", or any outcome nobody could observe as pass/fail. | required |
| honest-unknowns | The candidate plan's risks/unknowns lines and any deferrals | Pass if uncertainty is stated as uncertainty (named unknowns, checked assumptions, explicit deferrals with a reason). Fail if the plan asserts as certain something the package does not show. | preferred |
| thread-direction | The candidate plan comment, read against the thread highlights (maintainer/owner/collaborator comments, linked or open PRs, patched builds, requested tests or approaches) | Pass if the thread holds no explicit maintainer direction, OR the comment acknowledges that direction and the plan follows it or says why it departs. Fail if a maintainer isolated a culprit, requested an approach or testing, or pointed at prior-art PRs, and the comment never engages it. | required |
| policy-compliance | The candidate plan comment, read against the repo-facts block's contribution policy (AI-use disclosure, templates, contributing asks) | Treat every package as AI-assisted work. Pass if the repo facts state no disclosure requirement, OR the comment contains the disclosure the stated policy requires. Fail if the policy requires disclosing AI use and the comment has none, or the comment breaks another explicitly stated contribution rule. | required |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check is `fail` or `unclear`: an `unclear` counts as a fail, because a plan that can't be verified from the package isn't ready to build from. `preferred` checks are reported but never change the verdict. Grade the plan, not its length: a terse plan that passes every required check is an accept.
